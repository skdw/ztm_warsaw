# ⚙️ Configuration

## 1. Get a key or token

The City runs two portals and the integration accepts the key of either one. It recognises which one you pasted and sends it only to the matching API.

| | New API (recommended) | Old API |
|---|---|---|
| Where | [dane.um.warszawa.pl/pl/key-api](https://dane.um.warszawa.pl/pl/key-api): enter a nick, accept the terms, download your token | [api.um.warszawa.pl](https://api.um.warszawa.pl) |
| Looks like | a long text in three parts separated by dots | `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` |
| Future | the City's current service | still works when this was written; the City published no date or promise for how long |

To move an existing entry from an old key to a token, use **Configure** on that entry (see *Change the key or token later* below); do not add a second entry for it: two entries for the same stop, pole and line cannot coexist, so the setup refuses the second one.

## 2. Add a sensor

**Settings → Devices & Services → Add Integration → Warsaw Public Transport**, then fill in:

| Field | Example | Notes |
|---|---|---|
| API key or token | | see above; spaces and line breaks at the start and the end are removed |
| Stop ID | `7009` | shared by all poles of a stop, see [Concepts](2.-Concepts) |
| Stop number | `01` | two digits, the number on the pole's sign |
| Line | `151` | the line must run on the day you add it: the City lists only the lines of the current day |

The setup checks the line and the timetable with the City before it creates anything. It creates one entry for the **line** (titled `Line 151`) with the stop as its first stop. The sensor is named after the line and the stop, for example `sensor.line_151_from_7009_01`.

The sensor always lists the next departure (the state) and the three after it (`Next 1` ... `Next 3`); there is nothing to choose.

## 3. Change the key or token later

**Settings → Devices & Services → Warsaw Public Transport → Configure** on an entry replaces its API key or token; the stop and the line stay. Use it to move an entry from the City's old API to the new one (a token) without removing it. The key is checked with the City before it is saved, a key the City rejects is refused, and the entry reloads when you save. An entry that still uses an old key shows a notice in **Settings → Repairs**: open it, paste the token and submit, or choose *Ignore* to keep the old key for now (the same step as **Configure**, so the key is checked with the City before it is saved).

## Several lines and stops

One entry is one **line**, and the stops it runs are listed under it. To add another stop of the same line, use **Add stop** on the entry (it asks only for the stop ID and the pole number and uses the key the line already has), or add the integration again with the same line: the stop joins the existing entry instead of making a second one. A different line is a different entry. Each stop is its own sensor and its own device (named `Line 525`, listed under the stop), and the line entry groups them. The same stop, pole and line cannot be added twice.

Entries made by 1.1.x (one stop each) are grouped by line when 1.2 starts for the first time: the entries of one line become one entry with its stops, and the sensors keep their names, IDs, areas and settings. If the stops of a line had different keys, the line uses a token when one of them was a token, otherwise the key of the oldest entry, and **Settings → Repairs** says so. Every stop becomes a device of its own (the area and the name you gave the line's device are copied to each), so an automation or a card that points at the old *device* needs choosing again; one that points at the sensor is not affected. An entry you had switched off is left as it was. There is no way back to 1.1.4 afterwards, so take a backup first if you want one.

## Walking time to a stop

**Settings → Devices & Services → Warsaw Public Transport**, then the menu (⋮) of a stop → **Reconfigure** and enter how many minutes it takes you to walk to that stop (0 to 120; 0 means none). The sensor of that stop then skips the departures that are sooner than that, because you could not catch them: its state is the first departure you can still reach, and `Next 1` to `Next 3` follow it. A departure leaves the sensor as soon as the time left is shorter than the walking time, so the state moves on by itself. The sensor shows the setting in the attribute `Walking time, Minutes` (only when it is set). The calendar and the timetable the City publishes are not changed. A stop of a line you had switched off before updating to 1.2 shows **Reconfigure** only after the next Home Assistant restart, which is when it joins its line.

## The calendar (optional)

Each entry also has a **calendar** entity, disabled by default because it holds every departure of the day (a calendar entry of one minute each, with the headsign, the stop and the brigade). Enable it in the entity settings of the entry. The calendar view then shows the whole timetable, and Home Assistant's **calendar trigger** can start an automation at a departure or at an offset from it ("eight minutes before a departure") without templates. It uses only the timetable the integration already holds, and has no events while the sensor is unavailable.

## The diagnostic sensor

Each entry also has a **Last update** sensor, disabled by default. Enable it in the entity settings to see when the timetable was last fetched successfully.
