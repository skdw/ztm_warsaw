# 🩺 Troubleshooting

## Questions people ask

**Do I have to restart Home Assistant after an update?** Yes. Home Assistant reads an integration's code only when it starts, so every custom integration needs a restart after an update. See [Installation](0.-Installation).

**My line says "The old API no longer works".** The City's old API (`api.um.warszawa.pl`) stopped answering on 21 October 2026, and the integration no longer asks it. The line keeps the timetable it had until the service day ends and then has none. To bring it back, replace the old key with a token: see [Configuration](1.-Configuration). The City's new host (`dane.um.warszawa.pl`) kept answering.

**The state is `unknown` in the evening.** This means that the last departure of the day has gone, or that the line does not run today. The *Status* sensor tells you which, and `Timetable, Last Departure` still says when the last bus left.

**The Vehicle entity has no pin.** Its `Status` attribute tells you why: `no_vehicle` (the bus has not started the line yet, or the City does not report it), `old_position` (the last position is more than three minutes old, for example a parked bus), `too_early` (the next departure is more than 15 minutes away, so nothing is asked), `city_unavailable`, `no_brigade` or `no_timetable`. Only entries with a token have the entity, and it is off by default. At night the City reports few vehicles.

## What does the state mean?

| What you see | Meaning | What to do |
|---|---|---|
| A time (timestamp) | the next scheduled departure | nothing |
| `unknown`, `Upcoming, Headsign` is `No service` | the line does not run today, or its last departure has passed | not an error; check [wtp.waw.pl](https://wtp.waw.pl) or call 19115 |
| `unavailable` | the City's API answered, but not with a timetable: the key or token was rejected, the stop, pole and line are not known, or the answer was in an unknown format | see below; the Home Assistant log has the reason (the key is never logged) |
| The integration is shown as *retrying setup* | the first load did not work | Home Assistant retries by itself; it ends when the City answers properly |

## Setup says "line not found" or "no departures"

The API lists only the lines that run today. A weekday-only line cannot be added on a Sunday. Check the stop ID and the pole number as well; the error message tells which one the City did not know.

## "Already configured"

The same stop, pole and line are already set up. To change the key of a working entry, use **Configure** on it (the re-authentication prompt below appears only when the City rejects the key). If you have an older pair of duplicates, Home Assistant shows a notice in **Settings → Repairs** for the later entry: remove one of the two.

## Home Assistant asks for a new key (re-authentication)

The old API answered "rejected key" three times in a row (the retries of a setup count too; an outage in between starts the count again). Enter a new key or token in the prompt. The stop and the line stay as they are, and a key is accepted even if the line does not run today. Until you do, the sensor stays `unavailable`.

The new API answers every rejected request in the same way as an outage, so a rejected token is not noticed at once: the sensor keeps the cached timetable until its service day ends and then becomes `unavailable`, and no prompt appears. If you revoked the token, enter a new one in **Configure** on the entry.

## The data look stale

After a good load, a timeout, a network error or a server error does not make the sensor `unavailable` at once: it keeps the last timetable and tries again every hour. It becomes `unavailable` only when that timetable is no longer valid (its service day is over and nothing is left of the night). Enable the **Last update** sensor to see when the data were last fetched.

## Early-morning departures are missing

The City publishes the new day's timetable overnight, and the two APIs may do it at different times (see [Concepts](2.-Concepts)). Until the API you use has the new day, the first departures of the morning (a tram that starts at 04:00, say) are not known to the sensor, so it does not show them. That is how the API behaves, not something the integration can change.

## Night lines

The City counts the whole night as part of the previous service day, so a bus at `24:50` or `26:20` is in that day's timetable. The integration shows it at 00:50 or 02:20.

## Reporting a problem

1. Open the integration's entry and choose **Download diagnostics**. The file shows the entry (the key or token is replaced by `**REDACTED**`) and the state of the timetable: the service day, the number of departures, the last error's class.
2. Open an [issue](https://github.com/solarssk/ztm_warsaw/issues) and attach the file. Say what you expected and what you saw.

Never paste a key or token into an issue. To report a vulnerability, see [Contributing](6.-Contributing).
